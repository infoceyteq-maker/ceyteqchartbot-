# Ceyteq architecture review

## Repository map

- `frontend/`: Next.js App Router workspace, local brand assets, responsive neumorphic interface, and route handlers under `app/api/`. `lib/brand.ts` is the single source for customer-facing contact/social links. The workspace is a new implementation, not the old compiled manager.
- `src/main.ts`: Express bootstrap, CORS, static assets, error handling and server startup. `src/api/routes/` mounts route brokers; `controllers/` delegate to services and integrations; `guards/` check API keys and instances; DTOs and JSON Schema validators define request shapes.
- `src/api/services/monitor.service.ts`: in-memory channel registry and persisted instance lookup. Every tenant operation should be scoped to its instance. `channel.service.ts` provides shared chat/contact/message functions. Channel implementations are in `src/api/integrations/channel/` (Baileys, Meta, and a legacy channel).
- `src/api/integrations/chatbot/`, `event/`, and `storage/`: optional bot, webhook/queue/socket, and S3/MinIO integrations. Chatwoot history import has a separate PostgreSQL connection to Chatwoot itself; it is not the primary Ceyteq database.
- `prisma/mysql-schema.prisma`, `prisma/mysql-migrations/`: primary schema and migration history used by TiDB/MySQL. PostgreSQL schemas/migrations remain for existing deployments. The new default is `mysql`; PostgreSQL deployments must explicitly set `DATABASE_PROVIDER=postgresql`. `runWithProvider.js` selects the correct files for Prisma commands and maps `DATABASE_URL` to the schema’s existing `DATABASE_CONNECTION_URI`. The API applies the same aliases at startup; existing variable names take precedence.
- `Dockerfile`, `frontend/Dockerfile`, `docker-compose.yaml`: separately built API and workspace. `Docker/` contains optional service/deployment examples. The old manager bundle and submodule were removed; `/manager` is disabled in the example configuration. If enabled, it redirects only to explicitly configured `FRONTEND_URL`.
- `LICENSE`, `NOTICE`, `TRADEMARKS.md`, `CHANGELOG.md`: upstream legal notices and historical release record, retained to preserve attribution and provenance.

## Request and trust boundaries

The browser talks only to same-origin Next.js routes. An administrator supplies an existing API key to `/api/session`; the server validates it with `GET /instance/fetchInstances`, encrypts it with AES-256-GCM using `CEYTEQ_SESSION_SECRET`, and issues a 12-hour HTTP-only, SameSite=Strict cookie. The key and TiDB URI are not included in frontend bundles or local storage. `/api/backend/...` accepts only explicitly listed methods and API paths, attaches the decrypted key server-side, limits request size, rejects redirects, and strips credentials/integration records from the instance list. It checks a custom same-origin header and mismatched Origin. Use HTTPS, restrict public ingress, and keep the session secret stable and private across replicas. Anyone holding the global API key has broad administrative privileges; the dashboard is not a multi-user identity or RBAC system.

Overview counts come from the API's per-instance Prisma counts. Activity is computed from the selected channel's latest 500 saved messages; it is not a comprehensive analytics system. Chat/contact lists load up to 100 entries and the conversation thread loads the latest 100 messages. Sample mode is explicitly labelled and cannot send messages or mutate real channels. The live UI supports core channel, text-message, contact and webhook operations; other existing API routes remain available to authorized API clients but are not all exposed as UI screens.

## TiDB and MySQL

The API uses Prisma's `mysql` provider over TCP, not a browser-side connection or a serverless TiDB adapter. TiDB Cloud's public endpoint requires TLS; use the cluster's connection string, strict certificate validation, and its CA where required. The current MySQL migration history uses foreign keys and other DDL; TiDB support varies by cluster/version. Test *the full migration chain and application flows* against the target TiDB cluster before production; no TiDB credentials or cluster were available in this checkout. Do not assume a PostgreSQL database can be converted simply by changing the provider: migrate data separately and validate it.

The pre-existing MySQL schema had drifted from the backend: `IsOnWhatsapp.lid` was removed by an old migration and the per-instance `Label` unique key was absent. The new `20261030000000_ceyteq_mysql_schema_parity` migration restores the column and adds the unique key. Before applying it to an existing database, check for duplicate non-null `(labelId, instanceId)` pairs and resolve them; the unique-index creation intentionally fails if duplicates remain. The earlier `20250918183910` migration drops `lid`, so back up/export those values before upgrading through it; the new migration restores the column, not lost values. Prisma migration deployment is opt-in in containers.

Core message lookup, status updates and JSON paths now select the correct Prisma path syntax for MySQL/TiDB versus PostgreSQL. Chat listing uses a parameterized MySQL/TiDB window query instead of PostgreSQL-only `DISTINCT ON` and JSONB syntax. Chatwoot's own import queries intentionally remain PostgreSQL-specific because they query Chatwoot's database. MySQL/TiDB and PostgreSQL builds should both be tested when changing the persistence layer.

## Compatibility and operational risks

- Existing public route names, `EVOLUTION`/`EvolutionBot` integration identifiers, historical migration names, Prometheus `evolution_*` metric names, and the existing S3 object-key prefix remain unchanged to avoid breaking clients, persisted records, dashboards or existing media. They are compatibility identifiers, not customer-facing branding. Existing users must retain their old database client name, Redis/queue prefixes, and configured storage bucket until they deliberately migrate them.
- The existing API returns privileged instance/integration data to authorized clients. The Next.js proxy deliberately exposes a reduced instance representation, but **do not expose the backend directly** to untrusted networks. Review API authorization, rate limiting, webhook destination controls, dependency security and observability for your deployment.
- A 12-hour encrypted cookie is a bearer credential, not a substitute for user accounts, revocation, MFA or per-user permissions. Rotate the session secret to revoke all dashboard sessions. Configure a trusted proxy to set the forwarded protocol correctly, and require HTTPS.
- Real WhatsApp connection, TiDB TLS, migration and message-delivery testing require external services and credentials. The sample workspace is not evidence that those services are connected. Validate recovery, throughput, backups, migration rollback, permissions and provider terms before launch.
- API telemetry is disabled by default and requires an explicit destination when enabled. Third-party service-specific telemetry remains subject to those services' settings.
